# AI Reassignment Engine Implementation Plan

## Feature Breakdown

### FOUNDATION

#### F01: Domain Model & Database Seeding
1. **Feature ID**: F01
2. **Feature name**: Domain Model & Database Seeding
3. **Purpose**: Establish the core data structures and populate initial test data.
4. **User story**: As a developer, I need a populated database so I can build features against realistic data.
5. **Business logic**: Define valid state transitions (e.g., Agent: AVAILABLE->OFFLINE).
6. **Backend work**: Spring Boot setup, JPA Entities (Agent, Order, ReassignmentSuggestion), Enums.
7. **Frontend work**: None.
8. **Database work**: Configure H2, write `data.sql` to seed 5 agents and 8 assigned orders.
9. **AI work**: None.
10. **Dependencies**: None.
11. **Complexity**: Low
12. **Priority**: MUST HAVE
13. **Acceptance criteria**: Application starts, database contains seed data, entities can be queried via repository.
14. **Test scenario**: Start app, query H2 console, verify 5 agents exist.

### CORE REASSIGNMENT

#### F02: Offline Detection & Affected Orders
1. **Feature ID**: F02
2. **Feature name**: Offline Detection & Affected Orders
3. **Purpose**: Detect state changes and identify orders needing reassignment.
4. **User story**: As the system, I need to know when an agent is offline and which orders are impacted to start replanning.
5. **Business logic**: When agent status = OFFLINE, find all their orders where status = ASSIGNED.
6. **Backend work**: Endpoint to update Agent status, Service method to find affected orders.
7. **Frontend work**: None.
8. **Database work**: Update agent status query, select orders by agent_id.
9. **AI work**: None.
10. **Dependencies**: F01
11. **Complexity**: Low
12. **Priority**: MUST HAVE
13. **Acceptance criteria**: Marking agent offline successfully returns list of affected orders.
14. **Test scenario**: Call `PUT /api/agents/1/offline`, verify response includes affected orders.

#### F03: Pluggable Routing & Rule-Based Strategy
1. **Feature ID**: F03
2. **Feature name**: Pluggable Routing & Rule-Based Strategy
3. **Purpose**: Provide a fast, reliable baseline reassignment logic and establish the abstraction.
4. **User story**: As operations, I need a logical fallback suggestion if AI is unavailable.
5. **Business logic**: Filter agents (AVAILABLE only), sort by `active_order_count` ascending, pick the first. Create `ReassignmentSuggestion`.
6. **Backend work**: Define `RoutingStrategy` interface. Implement `RuleBasedRoutingStrategy`. Integrate into the reassignment loop (F02).
7. **Frontend work**: None.
8. **Database work**: Save generated `ReassignmentSuggestion` to DB with status `PENDING`.
9. **AI work**: None.
10. **Dependencies**: F02
11. **Complexity**: Medium
12. **Priority**: MUST HAVE
13. **Acceptance criteria**: The system automatically generates a PENDING suggestion using the rule-based logic when an agent goes offline.
14. **Test scenario**: Trigger F02, query Suggestions table, verify a new suggestion exists for the agent with least load.

### UI

#### F06: Operations Dashboard
1. **Feature ID**: F06
2. **Feature name**: Operations Dashboard
3. **Purpose**: Display pending reassignments to Operations.
4. **User story**: As an Ops manager, I want to see a queue of pending suggestions with their reasoning so I know what needs attention.
5. **Business logic**: Fetch all `PENDING` suggestions and join with Order/Agent details.
6. **Backend work**: `GET /api/suggestions/pending`.
7. **Frontend work**: React scaffolding (Vite), fetch data (polling every 5s), render list/cards showing order, recommended agent, score, reasoning.
8. **Database work**: Query `ReassignmentSuggestion` by status.
9. **AI work**: None.
10. **Dependencies**: F03
11. **Complexity**: Medium
12. **Priority**: MUST HAVE
13. **Acceptance criteria**: React UI displays pending suggestions retrieved from the backend.
14. **Test scenario**: Open UI, see 2 pending suggestions generated by the backend tests.

#### F07: Approve/Reject Actions
1. **Feature ID**: F07
2. **Feature name**: Approve/Reject Actions
3. **Purpose**: Allow ops to execute or dismiss the AI's recommendation.
4. **User story**: As an Ops manager, I want to click 'Approve' to instantly reassign the order.
5. **Business logic**: 
    - Approve: Update Suggestion to APPROVED. Update Order's `assigned_agent_id`. Update Agent's `active_order_count`.
    - Reject: Update Suggestion to REJECTED.
6. **Backend work**: `POST /api/suggestions/{id}/approve`, `POST /api/suggestions/{id}/reject`. Transactional updates.
7. **Frontend work**: Add Approve/Reject buttons to UI cards. Re-fetch list on success.
8. **Database work**: Update order, agent, and suggestion tables in a single transaction.
9. **AI work**: None.
10. **Dependencies**: F06
11. **Complexity**: Medium
12. **Priority**: MUST HAVE
13. **Acceptance criteria**: Approving a suggestion removes it from the queue and updates the order's assigned agent in the database.
14. **Test scenario**: Click Approve on UI. Refresh page. Verify suggestion is gone. Query DB, verify order is assigned to new agent.

### AI

#### F04: Gemini AI Routing Strategy
1. **Feature ID**: F04
2. **Feature name**: Gemini AI Routing Strategy
3. **Purpose**: Use LLM to generate intelligent reassignments with plain-English reasoning.
4. **User story**: As operations, I want AI to consider context and explain *why* it recommends an agent so I can trust it.
5. **Business logic**: Send order details and AVAILABLE agent roster to Gemini. Parse JSON response into `ReassignmentSuggestion`.
6. **Backend work**: Implement `LLMGateway` using RestClient. Implement `AIRoutingStrategy`. Prompt engineering.
7. **Frontend work**: None.
8. **Database work**: Save suggestion with confidence score and reasoning.
9. **AI work**: Construct prompt, parse structured JSON output.
10. **Dependencies**: F03
11. **Complexity**: High
12. **Priority**: MUST HAVE
13. **Acceptance criteria**: System sends prompt to Gemini, parses response, and saves a suggestion with reasoning and score.
14. **Test scenario**: Set AI as active strategy, mark agent offline, verify DB contains suggestion with reasoning text.

#### F05: Runtime Strategy Toggling & Fallback
1. **Feature ID**: F05
2. **Feature name**: Runtime Strategy Toggling & Fallback
3. **Purpose**: Switch routing brains without restart and handle AI failures.
4. **User story**: As an admin, I want to switch between Rule and AI routing dynamically. If AI fails, I don't want the system to crash.
5. **Business logic**: Maintain active strategy state. If active=AI and AI throws exception, catch and call active=Rule.
6. **Backend work**: Endpoint to toggle active strategy. Try-catch block in AI routing delegating to Rule fallback.
7. **Frontend work**: None.
8. **Database work**: None.
9. **AI work**: None.
10. **Dependencies**: F03, F04
11. **Complexity**: Medium
12. **Priority**: MUST HAVE
13. **Acceptance criteria**: API call flips the strategy; subsequent offline events use the new strategy. AI failure falls back to rule.
14. **Test scenario**: Toggle to Rule, trigger offline, verify rule output. Toggle to AI, trigger offline, verify AI output. Supply bad API key to force AI failure, verify rule fallback executes.

## Implementation Order

To guarantee a working system early and fit within the 2.5-hour constraint, features will be executed in this exact sequence:

1. **F01**: Domain Model & Database Seeding *(Foundation)*
2. **F02**: Offline Detection & Affected Orders *(Core Reassignment)*
3. **F03**: Pluggable Routing & Rule-Based Strategy *(Core Reassignment)*
   > **Milestone Checkpoint**: At this stage, the backend can automatically reassign orders using simple math. This establishes our baseline.
4. **F06**: Operations Dashboard *(UI)*
5. **F07**: Approve/Reject Actions *(UI)*
   > **Milestone Checkpoint**: We now have a full end-to-end working MVP (Backend + Frontend) using Rule-based logic.
6. **F04**: Gemini AI Routing Strategy *(AI)*
   > **Milestone Checkpoint**: AI is now powering the system via the pluggable interface.
7. **F05**: Runtime Strategy Toggling & Fallback *(AI)*
8. **F08**: Demo Prep & End-to-End Polish *(Polish)*
